# 建立知識的規則

本文件規定在知識庫建立或修改知識時遵守的規則。這些規則適用於所有分類；各分類特有的規則，例如文件類型、生命週期與範本，寫在該分類的 `README.md`。

知識只能在 ADE repo 建立與修改。ADE 中的知識庫是唯讀副本，update 時會被整個覆蓋；在 ADE 中需要修改知識時，先依 `ade-contribute` 取得 ADE repo 的工作副本，修改工作副本後送回 ADE repo。

## 收錄

判斷一項內容是否收進知識庫，遵守下列規則：

- 能以文字描述的內容都可以收錄，例如流程、服務規格、概念與事件。
- 同一份知識應只有一個權威來源。已有權威來源的知識，例如服務 repo 記錄的建置與測試步驟，不應複製進知識庫，只記錄取得的方式或引用它；兩者不一致時，以權威來源為準。
- 知識庫不得放可執行的腳本，腳本屬於 skill。知識的內文可以用程式碼區塊附上說明用的指令或範例。
- 人不透過 agent 做這件事時也需要知道的內容，寫在知識；只有 agent 執行時才需要的內容，例如與使用者互動的方式，寫在 skill。skill 以引用指向知識，不得重述知識的內容。

## 查找既有知識

建立知識之前，先依下列步驟確認知識庫中沒有同一份知識：

1. 讀知識庫根目錄的 `CONTEXT.md`，以 `_Avoid_` 把要找的用詞換成正式名詞。
2. 以正式名詞 grep 知識的內文。
3. 以正式名詞的英文名 glob 檔名。
4. 命中多份檔案時，先讀各檔案 frontmatter 的 `description`，選出需要的檔案再讀全文。

搜尋找不到時，從知識庫根目錄的 `README.md` 沿入口檔逐層往下找。已有同一份知識時，修改它，不另建一份。

## 放置

決定知識放在哪裡，遵守下列規則：

- 從知識庫根目錄 `README.md` 的導覽選出分類，再讀該分類的 `README.md` 確認定位與文件類型。
- 會一起修改的內容必須放在同一個知識單位；會各自修改的內容應分成不同的單位。判斷時問的是「這段內容改變時，還有哪些內容必須跟著改」，而不是主題是否相近。
- 同一個單位內，不同讀者或不同時機只需要其中一部分時，應拆成多份檔案，由入口檔導覽。篇幅長不構成拆檔的理由；拆開後總是一起讀的，應合併回一份。
- 入口檔的導覽無法讓讀者一次看完並選出下一步時，應多分一層。層數與每層的項目數不設上限。

## 檔案

知識單位是一份 `.md` 檔，或一個帶有入口檔 `README.md` 的資料夾。檔案遵守下列規則：

- 每個單位必須有一份 `.md` 作為主要檔案。包含其他格式檔案的單位必須是資料夾；這些檔案是附件，不帶 id，由同一單位的 `.md` 以相對路徑引用。
- 單位由檔案長成資料夾時，原檔的 id 移到資料夾的 `README.md`。
- 檔名使用小寫 kebab-case，應使用詞彙表中正式名詞的英文名，例如詞條「結帳（Checkout）」對應 `checkout.md`。
- 全大寫的檔名保留給慣例檔名：入口檔 `README.md`、由程式產生的索引檔 `INDEX.md`、詞彙表 `CONTEXT.md`。`INDEX.md` 不得手寫。
- `_` 開頭的檔案是範本，例如 `_template.md`，以範本建立新檔時才產生 id。

## frontmatter

知識庫內的 `.md` 必須在 frontmatter 寫下表的兩個欄位；知識庫根目錄的檔案、`INDEX.md` 與 `_` 開頭的範本除外：

| 欄位 | 內容 |
|---|---|
| `id` | 6 位小寫十六進位，建立檔案時以指令產生，不得自行編寫；在分類內必須唯一，建立後不得更改 |
| `description` | 一句話說明這份知識是什麼，寫內容，不寫何時閱讀 |

產生 id 的指令如下，輸出一個 6 位的十六進位字串：

```sh
node -e "console.log(require('crypto').randomBytes(3).toString('hex'))"
```

frontmatter 寫在檔案的最開頭，例如：

```md
---
id: 3f9a2c
description: 結帳流程中訂單、付款與庫存的狀態轉換規則。
---
```

分類或文件類型需要的其他欄位，例如狀態與日期，由該分類的 `README.md` 定義。會被程式或 skill 讀取的屬性應寫在 frontmatter，內文不重述。

## 入口檔

知識庫的每個資料夾都必須有 `README.md`，依序包含下列內容：

1. 標題。這一層收錄什麼寫在 frontmatter 的 `description`，內文不重述。
2. 本層特有的規則；上層已經定義的規則不重複，沒有就省略。
3. 導覽。

導覽的寫法依資料夾的性質決定，如下表所示：

| 資料夾的性質 | 導覽的寫法 |
|---|---|
| 主題型：各項內容不同 | 逐項列出，每一項寫明在什麼處境下閱讀，不寫內容摘要 |
| 集合型：一筆一檔、結構相同 | 寫檔名規則與新增方式，不逐筆列出 |

新增、搬移或刪除單位時，必須同步修改上層入口檔的導覽。

## 引用

引用另一份知識時，遵守下列規則：

- 引用必須寫成 markdown 連結，連結目標是符號位址 `kb:<分類>/<id>`，例如 `[結帳的狀態規則](kb:specs/3f9a2c)`。分類是知識庫根目錄下的第一層資料夾。
- 連結文字描述目標的內容，讓讀者不必跳轉就能判斷是否需要閱讀。
- 符號位址只指向檔案，不指向檔案內的章節。
- 描述知識庫的結構或指定建檔位置時，寫路徑，例如「新的規格建在 `knowledge/specs/`」。

解析符號位址時，在知識庫的 `<分類>/` 下搜尋 frontmatter 為 `id: <id>` 的檔案。

## 關聯

兩份知識之間的關聯遵守下列規則：

- 同一個關聯必須只記錄在一側。有依賴關係時，由依賴方，即需要對方才能被理解或執行的一側，記錄並指向被依賴方，例如規格列出構成功能的服務；沒有明確依賴的對等關係，由後建立的一側記錄。
- 從被依賴方出發時，以搜尋找出依賴它的知識：有 id 時搜尋 id，以名稱指稱時搜尋名稱。
- 刪除或改名被依賴的知識之前，必須先以搜尋找出所有依賴方並一併修改。

## 用詞

知識必須使用詞彙表的正式名詞，不得使用詞條中 `_Avoid_` 列出的同義詞。需要詞彙表沒有的專有名詞時，必須先加入詞彙表。詞條的格式如下：

```md
**結帳（Checkout）**：
顧客確認購物車內容並完成付款的流程。
_Avoid_：下單、checkout 流程
```

## 驗證

修改完成後，在 ADE repo 的根目錄執行下列指令。第一次執行前先以 `pnpm install` 安裝依賴：

```sh
node cli.js check
```

指令輸出 `ADE check passed` 時，代表入口檔、frontmatter 與引用的語法正確。check 無法判斷放置位置、`description` 的品質與關聯是否只記一側，這些由 review 確認。
