# 符號位址

本文件規範知識庫內的引用如何記錄：引用一律以符號位址指向知識檔案，符號以建立時產生、不可更改的 id 定址。知識單位與分類的定義見[知識的形式原則](./README.md)，檔名的規則見[檔名](./naming.md)，考慮過的其他做法見[以 id 定址的決策紀錄](../../adr/0004-address-knowledge-by-immutable-random-id.md)。

知識檔案會改名、搬移，單位也會延伸：檔案長成資料夾、資料夾多分一層。路徑與檔名都會在這些變動中改變；id 在建立後不變，引用因此不受影響。

## 形式

符號位址的形式為 `kb:<分類>/<id>`，例如 `kb:process/a3f9c2`。分類是知識庫根目錄下的第一層資料夾，符號不寫中間層。

符號在分類內解析：指向分類內任何深度、frontmatter 的 `id` 與符號相符的檔案。

## id

id 遵守下列規則：

- id 為 6 位小寫十六進位，建立知識檔案時以指令產生，不得自行編寫。
- `.md` 檔的 id 寫在 frontmatter 的 `id` 欄位；YAML 檔寫在頂層的 `id` 欄位。
- id 在分類內必須唯一。
- id 建立後不得更改。檔案改名、搬移時 id 不變；單位由檔案長成資料夾時，id 移到資料夾的 `README.md`。

產生 id 的指令如下，輸出一個 6 位的十六進位字串：

```sh
node -e "console.log(require('crypto').randomBytes(3).toString('hex'))"
```

id 由指令產生，因為自行編寫的值不夠隨機，重複的機率較高。

## 需要 id 的檔案

手寫的知識檔案都必須有 id。下表列出各類檔案是否需要 id：

| 檔案 | 是否需要 id | 理由 |
|---|---|---|
| 一般知識檔案 | 需要 | 會被引用 |
| 入口檔 `README.md` | 需要 | 資料夾形態的單位以它的 id 被引用 |
| 索引檔 `INDEX.md` | 不需要 | 由程式產生，不是知識 |
| `_` 開頭的範本 | 不需要 | 範本是建檔的起點，不是知識；以範本建立新檔時才產生 id |

## 書寫方式

引用必須寫成 markdown 連結，連結目標是符號位址，例如：

```md
狀態的判讀方式見[開發流程的狀態規則](kb:process/a3f9c2)。
```

連結文字描述目標的內容，讓讀者不必跳轉就能判斷是否需要閱讀。引用方在引用時必然知道目標的內容，因此由引用方撰寫連結文字。

符號指向一份檔案，不指向檔案內的章節。

## 符號與路徑的分工

符號與路徑 `knowledge/…` 服務不同的目的，依下表選用：

| 目的 | 寫法 | 例子 |
|---|---|---|
| 引用一份知識 | 符號位址 | 「狀態的判讀方式見[開發流程的狀態規則](kb:process/a3f9c2)」 |
| 描述知識庫的結構，或指定建檔位置 | 路徑 | 「新的規格建在 `knowledge/specs/`」 |

## 落實方式

本文件的原則依下表落實：

| 原則 | 落實的機制 |
|---|---|
| 符號能解析，且在分類內只對應一份檔案 | runner 的檢查：辨識所有連結目標以 `kb:` 開頭的連結，解析失敗或對應到多份檔案時報錯 |
| 需要 id 的檔案都有 id | runner 的檢查 |
| id 不得更改 | runner 的檢查間接保證：改了 id 而未同步修改引用時，引用解析失敗；ADE repo 以外的引用由 skill 的規則約束 |
| 以指令產生 id、引用寫成連結 | skill：建立知識的 skill 以指令產生 id，引用時寫成連結；seed：初始內容作為範例 |
