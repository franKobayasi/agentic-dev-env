# 知識單位與樹

本文件規範知識單位的邊界，以及知識何時拆成多份檔案、何時多分一層。知識單位、樹與兩個衡量標準的定義見[知識的形式原則](./README.md)。

## 單位的邊界

單位的邊界依管理成本決定：會一起修改的內容必須放在同一個單位，會各自修改的內容應分成不同的單位。判斷時問的是「這段內容改變時，還有哪些內容必須跟著改」，而不是「這些內容的主題是否相近」。

## 主要檔案與附件

知識單位不限制檔案格式，但必須有一份 `.md` 作為主要檔案，單位的 id 寫在它的 frontmatter，見[符號位址](./addressing.md)。包含非 `.md` 檔案的單位必須是資料夾，主要檔案是資料夾的 `README.md`。例如收錄一張架構圖時，單位是 `architecture/README.md` 加上 `architecture/diagram.png`。

非 `.md` 的檔案是附件，遵守下列規則：

- 附件不帶 id，由同一單位的 `.md` 以相對路徑引用。
- 其他單位引用附件時，指向附件所屬單位的符號。
- 需要指稱個別附件時，以名稱指稱，例如服務清單中以服務名稱指稱各服務的描述檔。

關聯以 id 建立，id 只寫在 `.md`，因此每個單位都能被引用，runner 也只需要解析一種寫入 id 的方式。考慮過的其他做法見[以 `.md` 為主要檔案的決策紀錄](../../adr/0006-markdown-as-primary-file-of-knowledge-unit.md)。

## 拆檔

拆檔依查找成本決定，遵守下列規則：

- 同一個單位內，不同讀者或不同時機只需要其中一部分時，應拆成多份檔案，並由入口檔導覽。
- 篇幅長不構成拆檔的理由。
- 拆開後讀者總是要把各部分一起讀時，應合併回一份檔案。

## 分層

入口檔的導覽無法讓讀者一次看完並選出下一步時，應多分一層。每一層只讓讀者回答一個問題，例如第一層回答「屬於哪個領域」，第二層回答「是該領域的哪個部分」。同一層同時依兩種依據分類時，讀者必須同時考慮兩件事，選錯的機率隨之升高。

## 兩個標準衝突時

管理成本與查找成本指向不同的切分方式時，依下表處理：

| 情況 | 處理方式 |
|---|---|
| 會一起修改，但分開閱讀 | 單位是一個資料夾，內部依讀者拆成多份檔案，由入口檔導覽 |
| 會各自修改，但經常一起閱讀 | 維持不同的單位，以[關聯](./relations.md)連接 |

## 數量

層數與每層的項目數不設上限，分層與拆檔以本文件的質性原則判斷。人為的數量限制會迫使內容違反單位的邊界：為了符合數字而拆開一起修改的內容，或合併各自修改的內容。

檢索效率不足時，改善的方向是檢索方式，例如搜尋或由程式產生的索引，而不是減少分層或限制數量。考慮過的其他做法見[不設上限的決策紀錄](../../adr/0001-no-depth-or-item-limits-in-knowledge-base.md)。

## 落實方式

本文件的原則依下表落實：

| 原則 | 落實的機制 |
|---|---|
| 單位的邊界、拆檔、分層、合併 | skill：建立知識的 skill 依這些原則決定內容的放置位置；seed：初始結構遵守這些原則，作為 ADE repo 演化時的範例 |
| 每個單位有 `.md` 主要檔案、附件位於帶有 `README.md` 的資料夾 | runner 的檢查 |
| 數量不設上限 | runner 的檢查：不得因層數或項目數而報錯 |
