# 知識之間的關聯由依賴方記錄

## Context and Problem Statement

關聯是樹以外的橫向引用。seed 中同一個關聯被記錄在多個位置：服務描述檔的 `specs` 欄位列出相關的 spec，spec 也要求連回服務；呼叫方的 `calls` 與被呼叫方的 `called_by` 記錄同一個呼叫關係。新增一份涉及兩個服務的 spec 時，必須修改三個檔案，漏改任何一個，兩側就不一致而無人察覺。問題是：關聯應記錄在哪一側？

## Decision Drivers

* 新增一份知識時，應只需要修改它自己。
* 兩側記錄同一個關聯時，一致性無法由人維持。
* 反向查找必須仍然可行。

## Considered Options

* 由依賴方記錄，反向查找以搜尋完成
* 由讀者出發的一側記錄
* 兩側都記，由 runner 檢查兩側一致
* 只記一側，由程式產生反向索引

## Decision Outcome

Chosen option: "由依賴方記錄，反向查找以搜尋完成", because 它讓新增知識只需要修改知識本身，被依賴方通常較穩定，不因依賴方的增減而修改；反向查找沿用已定案的搜尋方式，不需要新的機制。

規則如下：

* 依賴方是需要對方才能被理解或執行的一側，例如 spec 依賴構成功能的服務，呼叫方依賴被呼叫方。
* 關聯由依賴方記錄，指向被依賴方；被依賴方不記錄反向的關聯。
* 沒有明確依賴的對等關係，由後建立的一側記錄。
* 反向查找以搜尋完成：搜尋被依賴方的 id 或名稱。

### Consequences

* Good, because 新增或刪除依賴方時，被依賴方不需要修改。
* Good, because 每個關聯只有一個記錄位置，不會出現兩側不一致。
* Bad, because 從被依賴方出發時看不到誰依賴它，必須搜尋。
* Bad, because 以名稱指稱的關聯不經過引用檢查，刪除被依賴方前必須搜尋名稱找出所有依賴方。
* Bad, because 是否雙向記錄無法機械判斷，只能由 skill 與 review 約束。

### Confirmation

以 review 確認：seed 的知識與建立知識的 skill 只在依賴方記錄關聯。

## Pros and Cons of the Options

### 由依賴方記錄，反向查找以搜尋完成

* Good, because 一個關聯只有一處需要維護。
* Bad, because 反向查找依賴搜尋，搜尋的可靠程度取決於用詞一致。

### 由讀者出發的一側記錄

* Good, because 讀者從常用的出發點就能看到關聯。
* Bad, because 讀者的出發點不只一種，最後仍然兩側都記。

### 兩側都記，由 runner 檢查兩側一致

* Good, because 從任一側出發都能直接看到關聯。
* Bad, because 每個關聯仍然要修改兩處，檢查只能發現不一致，不能減少修改。

### 只記一側，由程式產生反向索引

* Good, because 一處維護，兩側都能直接查看。
* Bad, because 需要新的產生機制；本地圖已將由程式產生的檢索改善列為範圍外，由觀察到的效率訊號觸發。

## More Information

由程式產生反向索引與本決策不衝突，日後可以在依賴方的記錄之上加上。本決策在知識框架的 wayfinder 地圖上定案，對應 bd 的 issue `ade-jeb.14`（關聯只記一側：定義方向）。
