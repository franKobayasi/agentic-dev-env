# 寫作指南

本指南規範本 repo 所有文件的內容與寫法，適用於 `docs/`、根目錄文件（`README.md`、`AGENTS.md`、`CHANGELOG.md`），以及 `seed/` 內的全部文件，包括知識庫、skill、常駐區段與 ADE repo 的根目錄文件。commit message 與程式碼註解不在本指南的範圍內。

本 repo 的文件同時服務兩種讀者：維護者與 agent。撰寫時以第一次接觸本 repo 的維護者能夠讀懂為標準；這個標準同樣讓 agent 不必自行推測被省略的前提。

## 規範用詞

規範性文件以固定用詞表達規則的強度。規範性文件是規定讀者該怎麼做的文件，例如本指南、開發指引與契約文件；說明性的段落照常書寫，不需要套用這些用詞。

下表列出三個強度的用詞：

| 用詞 | 意思 | 違反時 |
|---|---|---|
| 必須、不得 | 沒有例外 | 造成錯誤，例如測試失敗或 ADE repo 無法運作 |
| 應、不應 | 預設遵守，有充分理由時可以例外 | 例外的理由寫在 commit message 或 PR 說明 |
| 可 | 視情況選擇 | 沒有後果 |

規則的強度由規則的作者決定。改寫既有文件時，原文未表明強度的規則不得自行判定，必須標記出來交由作者確認。

## 內容

本節規範文件寫什麼，以及如何組織論述。

### 語域

文件必須使用專業書面語。內容難以理解時，應補上被省略的前提，而不是改用口語。例如「讓比對跑得快」應寫成「加速比對」，「用不到」應寫成「不需要」。

術語應保留原文，第一次出現時用一句話交代它是什麼。必須說明的是本 repo 自行定義的詞，例如 seed、hub、契約 A；通用的技術詞，例如 symlink、frontmatter，不需要說明。縮寫第一次出現時必須展開，例如「ADE（Agentic Dev Environment）」。

### 論述順序

每份文件必須以一段概述開頭，說明本文涵蓋什麼，以及閱讀前需要知道什麼。各節應先寫結論或規則，再寫理由與細節。

需要讀者比較或判斷的內容應使用表格，欄位即判斷的維度。例如比較幾種做法時，欄位寫「機制」、「代價」、「適用情境」，而不是先用段落敘述再歸納結論。

### 銜接與預期結果

表格、清單與程式碼區塊之前必須有一句引導句，說明接下來的內容是什麼。引導句應是完整的句子，例如「下表列出 `hub/` 各部分在工作目錄中的去向：」，而不是「`hub/` 的去向：」。

讀者親手執行的步驟之後必須寫預期結果，讓讀者能判斷是否做對，例如「所有連結都能解析時，代表 seed 內的路徑寫法正確。」描述程式行為的步驟清單不需要預期結果。

程式碼區塊必須在前後的段落中說明其作用，不得只靠程式碼內的註解解說。

### 人稱

說明性的句子不寫主詞，例如「相對連結必須在 ADE repo 內檢查」。操作步驟使用祈使句，例如「執行 `node test.js`」。

同一段內容只涉及一種角色時，不寫主詞。涉及兩種以上的角色時，例如上游維護者、ADE repo 維護者、團隊成員與 agent，必須寫出角色名稱，讓讀者分辨規則約束的對象。

### 時態

文件只寫現況，不寫異動日期，也不寫「原本是 X，後來改成 Y」。現況之所以如此的理由與機制屬於現況，應保留。

異動的原因寫在 commit message；考慮過多種做法、會約束未來的決定寫成決策紀錄（ADR）。`CHANGELOG.md` 與決策紀錄本身就是在記錄異動，不受本節約束。

### 歸屬

同一件事只寫在一份文件，其他文件用連結指向它。入口文件可放一行摘要加連結，摘要不得超過一行。

## 寫法

本節規範文件的排版與格式。

### 標題

標題必須遵守下列規則：

- 一級標題只用於文件標題，章節從二級標題開始。
- 標題層級不得跳級，例如二級標題之下直接接四級標題。
- 兩個標題之間必須有內文。
- 一節之下不應只有一個子節；只有一個時，取消子節。
- 標題不得包含 code span 或連結。

### 清單

無序清單用於並列的項目，有序清單用於有先後順序的步驟。

清單項目的標點依項目的形式決定：完整的句子以句號結尾；短語、名詞或「名稱：說明」格式不加句號。以粗體句開頭的項目視為完整句子，粗體句與後續說明都以句號結尾。同一個清單內的項目必須是同一種形式。

### 表格

表格用於比較、對照與判斷。表格之前必須有引導句，引導句的規則見「銜接與預期結果」。

### 提示

提示是從內文獨立出來、提醒讀者特別留意的段落。依後果能否復原分成三級：

| 標籤 | 用在 | 例子 |
|---|---|---|
| `**備註**：` | 補充資訊，不影響操作是否正確 | 暫存目錄會在 session 結束後清除 |
| `**注意**：` | 容易做錯，但可以發現、可以修正 | 常駐區段不得命名為 `CLAUDE.md` |
| `**警告**：` | 造成難以復原的後果，或影響其他人 | issue 內容推送後即公開 |

冒號放在粗體之外。標籤後面緊接粗體文字時，標籤不加粗，例如「注意：**不得**直接編輯」。

### 連結

連結文字依讀者需要的資訊決定：

- 讀者需要了解某件事時，連結文字描述目標的內容，例如「見[依賴關係與相容性契約](./dependency-contract.md)」。描述的是內容，不必照抄目標文件的標題。
- 讀者需要知道或操作某個檔案時，連結文字寫檔名並放在 code span 內，例如「修改 [`bin/create.js`](../bin/create.js)」。

讀者會打開並修改該檔案時，視為操作；只閱讀其內容時，視為了解。連結文字不得使用「這裡」、「此連結」這類不帶資訊的詞。

### 程式碼與識別字

路徑、檔名、指令、程式碼識別字與設定鍵必須放在 code span 內。多行的程式碼或指令必須使用程式碼區塊，並標明語言，例如 `sh`、`js`。

### 中英混排與標點

中文與其他文字混排時，遵守下列規則：

- 中文與英文、數字、code span 之間留一個半形空格，例如「本 repo 的 `seed/` 有 2 個子目錄」。
- 中文句子使用全形標點：，。、；：「」（）。
- 中文的並列使用頓號，例如「維護者、團隊成員與 agent」。

### emoji

文件不得使用 emoji。嚴重度與狀態改用提示標籤或文字表達。

例外是工具依賴精確比對的固定標記，例如 spec 的尚未實作標記；這類標記屬於機器契約，修改時必須同步修改比對它的工具與 skill。

### 段落

一個段落寫成一行，不在句子中間斷行。斷行會讓 diff 難以閱讀，並讓搜尋漏掉跨行的詞句。
